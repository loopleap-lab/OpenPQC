# Security policy

OpenPQC is research-grade code: an implementation of FIPS 203 (ML-KEM), FIPS 204 (ML-DSA) and FIPS 205 (SLH-DSA) with
SYCL backends for GPUs. It is not a validated cryptographic module, and it is not yet hardened for production; its
opt-in FIPS 140-3 mode ([docs/FIPS-140-3.md](docs/FIPS-140-3.md)) is designed for FIPS 140-3; not validated. This file
says how to report a vulnerability, which configurations are tested, how mature the code is, which issues are known to
be open, and what the review of October 2026 found. [docs/SECURITY-NOTES.md](docs/SECURITY-NOTES.md) says what an
integrator must know: constant time, randomness, threads, stack, what is not destroyed, the GPU backends.

## Reporting a vulnerability

Report it privately, not in a public issue: use the repository's private vulnerability reporting ("Security", then
"Report a vulnerability", at https://github.com/UCF-ML-Research/OpenPQC). If that form is not available, open an issue
that asks the maintainers for a private channel, without any detail of the problem. Please include the commit, the
compiler and its version, the build type and options, the target processor and, for the GPU backends, the SYCL
implementation, the device and the driver, and a way to reproduce the problem.

What counts: anything that makes an output differ from FIPS 203, 204 or 205, a secret that reaches a branch, a memory
address or memory that should have been wiped in a configuration this file lists as tested, memory-safety errors,
a failure that is reported as success, and documentation that claims more than the code does. Issues already listed
below need no report, unless you can show that they are worse than described.

There are no releases yet: fixes go to the `main` branch, and only `main` is maintained.

## Maturity and scope

**What OpenPQC is.** A research-grade implementation of FIPS 203 (ML-KEM), FIPS 204 (ML-DSA) and FIPS 205 (SLH-DSA),
written to follow the text of the standards, with a C API and SYCL backends that run batches of operations on GPUs. It
has no release yet (the version number that the source tree carries, 0.3.0, which `openpqc_version()` returns, is not a
release), and the API and ABI may change. It has install rules, a CMake package and pkg-config files; the library is
static by default and shared on request, and a shared build exports the C APIs only.

**Not a FIPS 140-3 module.** It is not a validated cryptographic module and has not been submitted for FIPS 140-3
validation. The ordinary build (the default) has no approved random bit generator (by default the randomness comes from
the operating system; an application can register one), no self-tests when the library is loaded or a GPU context is
created (so an ordinary GPU build has no known-answer check of the device), no pair-wise consistency tests after key
generation, no integrity test, no error state, no service indicator and no defined module boundary; the FIPS 140-3 mode
(below) has the others, and in place of the first an SP 800-90A HMAC_DRBG (not CAVP-tested; seeded by the operating
system, whose source has no identified ESV certificate). The testing interfaces (randomness given by the caller, the
internal functions) are not in the library `openpqc` but in `OpenPQC::testing`, which is built only for the tests,
benchmarks and examples and never installed (review finding M13; test `production_symbols`); the shared GPU library
`openpqc_sycl` exports the GPU API (`openpqc/sycl.h`) only (its testing interfaces are in `OpenPQC::sycl_testing`, never
installed; test `sycl_exports`), while a static `openpqc_sycl`, which the FIPS 140-3 mode refuses, still contains the
backends' own functions, their `_derand` functions among them, which no installed header declares. Where FIPS 140-3 is
required, use a validated module; OpenPQC can serve as an independent implementation to cross-check it. Passing NIST's
published ACVP vectors is not a CAVP certificate.

**FIPS 140-3 mode.** Configured with `-DOPENPQC_FIPS140_3=ON` (x86-64 Linux with GCC or Clang), the build makes the
shared library `libopenpqc` a module designed for FIPS 140-3; not validated: no laboratory has tested it, no CAVP
certificate covers its algorithms, and nothing has been submitted to the CMVP. The module exports only its services (the
C APIs of the 18 parameter sets, the runtime-selected API and `opqc_randombytes`, with the version, the algorithm table,
`opqc_zeroize`, `opqc_set_randombytes`, which refuses, `opqc_fips_mark_non_approved` and the functions of
`openpqc/fips.h`: 195 functions). When it is loaded it checks its own file (HMAC-SHA-256 over every loaded segment,
against the value stored after the link) and runs a known-answer test of each algorithm; every key generation runs a
pair-wise consistency test; any failure, of the entropy source or the DRBG too, puts it into one error state, in which
every service returns `OPENPQC_ERR_ERROR_STATE` (-12) until it is loaded again (`openpqc_fips_status()`), and a service
during whose computation the module entered its error state returns -12 with its outputs zeroized (a key generation
whose own pair-wise consistency test failed returns `OPENPQC_ERR_PCT`, -6, with its keys zeroized). After each service,
`openpqc_fips_service_approved()` tells the calling thread whether it was an approved service that succeeded:
`keygen_from_seed` of ML-KEM and ML-DSA is approved as the import of a key pair in its seed format (NIST's PQC FAQ),
while ML-DSA's key checks and HashML-DSA or HashSLH-DSA with a pre-hash weaker than the parameter set are computed but
not approved. Every random value comes from an HMAC_DRBG (SP 800-90A, SHA-512, 256-bit strength; not CAVP-tested) inside
the module, seeded from `getrandom`; the module has no SP 800-90B entropy source, so the operating system's must be
validated (an ESV certificate) where the module is used, and without one the module cannot be validated there.
`opqc_set_randombytes` is refused. The module relies on the C library and the dynamic loader it is linked against: in a
process where any function it imports (`getrandom`, `getpid`, `__tls_get_addr` and the others the security policy lists)
is replaced or interposed, by whatever mechanism, none of its guarantees holds, its entropy input, error state and
indicator among them (the security policy draft, Section 6.2); it defines the memory functions it calls itself, so that
its integrity test and zeroization do not go through the C library. The header-only C++ APIs, the GPU library and the
testing interfaces are outside the module, and the GPU services are not approved (in this mode the GPU library also
tests every key pair it generates, every context runs a known-answer test when it is created, and a GPU call checks
the module's state again once its work is done, so that in this mode the GPU calls wait for their work). In a FIPS
build NIST's ACVP vectors also run through the sealed module itself (`fips_vectors_*`). The mode was developed on the
branch `fips140-3`; the review has not verified it. [docs/FIPS-140-3.md](docs/FIPS-140-3.md) gives what is done and what
remains (among it the entropy path through the C library, a laboratory, the CAVP certificates, the entropy source's
validation, a CI job), and [docs/FIPS-140-3-security-policy.md](docs/FIPS-140-3-security-policy.md) the draft of the
security policy.

**What is checked.** Every NIST ACVP case in the suite, the known-answer tests, the Wycheproof vectors of ML-KEM and
ML-DSA, and byte identity with the reference implementations; the GPU backends are byte-identical to the CPU library
on the devices above. [tests/README.md](tests/README.md#status) lists the tests of each group, and [Review
history](#review-history) says what an independent review ran.

**Side channels and secrets.** The project's valgrind tests check that secret data decides no branch and no memory
address, on x86-64 Linux, for the operations the tests run, with copies of the libraries that the tests compile (with
`OPQC_CT_TESTING`, without the x86-64 extensions that valgrind cannot decode), and for ML-KEM's Encaps and Decaps also
with the library as built, by GCC 16 and Clang 23, at the levels listed in the
[security notes](docs/SECURITY-NOTES.md#constant-time-what-is-checked-and-where). No
constant-time property is claimed for other compilers, other processors or the GPU. On the CPU, the schemes destroy
seeds, keys, shared secrets and their secret intermediate values (FIPS 203 §3.3, FIPS 204 §3.6.3, FIPS 205 §3.1);
ML-KEM (unless it is built with `OPENPQC_MLKEM_STACK_BURN=OFF`) and SLH-DSA also overwrite the stack below each call,
while ML-DSA's values destroy themselves and Core clears the frames of its hash functions; what lies beyond that is
in the security notes ([What is not destroyed](docs/SECURITY-NOTES.md#what-is-not-destroyed)). Physical attacks
(power, electromagnetic) and fault attacks are out of scope: there are no countermeasures such as verification after
signing.

**Out of scope.** Physical attacks (power, electromagnetic, faults), and attackers who can read the process's memory
while an operation runs. What an operation leaves in memory after it has returned is in scope (the libraries destroy
their secret intermediate values), except where the table below says otherwise. An ML-KEM library built with
`OPENPQC_MLKEM_STACK_BURN=OFF` still destroys the values its code names, but not the copies that the compiler keeps in
stack slots of its own ([src/ML/KEM/README.md](src/ML/KEM/README.md#choices-that-differ-from-mlkem-native)).

**Intended use.** Research, interoperability testing and GPU batch experiments on hardware the operator controls. Read
this file and [docs/SECURITY-NOTES.md](docs/SECURITY-NOTES.md) before using it anywhere else.

The scheme READMEs ([ML-KEM](src/ML/KEM/README.md), [ML-DSA](src/ML/DSA/README.md),
[SLH-DSA](src/SLH/DSA/README.md)) and the C headers document each contract in full: return codes, the state of the
outputs after a failure, what is destroyed, the stack, the threading rules of the GPU contexts.

## Review history

**What the review checked.** In October 2026 an independent review ran the CPU library against every NIST ACVP test
case in the project's suite (435 ML-KEM, 1335 ML-DSA and 1248 SLH-DSA cases), the known-answer tests and the
Wycheproof ML-KEM vectors. In every comparison made, its outputs were byte-identical to the reference implementations
(mlkem-native, the Dilithium and SPHINCS+ references), and they agreed with OpenSSL 3.6.5. The GPU backends returned
the same bytes as the CPU library on an NVIDIA RTX 3050 and an Intel Iris Xe, with DPC++ and AdaptiveCpp, on seven
device and toolchain combinations (for SLH-DSA the review ran five of them, the project's own runs all seven). All
testing used x86-64 Linux with GCC 16 and Clang 23. Windows with MSVC, macOS, ARM and RISC-V processors and AMD GPUs
have not been tested.

Since then the suite has gained Wycheproof's ML-DSA vectors (`mldsa_wycheproof`) and NIST's ACVP vectors of SHA-2, SHA-3
and SHAKE (`core_hash_acvp`: the messages of whole bytes), both network tests, which the review ran from fresh downloads
in its re-verification of 2026-11-08 (GCC build); and, after it, the 40 large-data tests of those vectors
(`core_hash_acvp_ldt`, labels `slow` and `network`), NIST's CAVP vectors of HMAC_DRBG (`core_drbg_cavp`) and RFC 4231's
of HMAC (`core_hmac`), which the review has not run.

**What was fixed.** The review (`docs/review-2026-10-21/` in the working tree of the maintainers) rated three issues
high, all in ML-KEM, and a number of others medium. The fixes of the three high issues and of most medium ones are in
this tree, most of them with a test that fails without it: Clang no longer turns ML-KEM's implicit rejection into a
branch; ML-KEM's operations no longer leave secret intermediate values on the stack; the ML-KEM GPU context takes a
lock, as the other two do; the GPU backends fail closed (status entries read as failures until a kernel decides them, a
context that has seen a device error refuses all further work, and a device error found through a context's queue no
longer ends the process) and the ML-KEM and ML-DSA contexts test the device when they are created; ML-DSA refuses
malformed private keys, and its stack needs are measured, documented and tested; every result of the C APIs must be
checked. In November 2026 a further fix round followed: ML-KEM's stack burn became a build option, the unprefixed
`randombytes()` hook gave way to `opqc_set_randombytes` and the build option `OPENPQC_EXTERNAL_RANDOMBYTES`, the ML-DSA
GPU signer refuses malformed private keys and its verification zeroizes what it computed, ML-DSA's `H` clears its
registers under Clang too, and tests were added (Wycheproof's ML-DSA vectors, NIST's ACVP vectors of the hash functions,
fresh randomness for ML-DSA and SLH-DSA, the constant-time test of ML-KEM's production library).

**What was re-verified.** By 2026-11-08 the review had re-verified the fixes up to that round on frozen copies: it rates
the three high findings fixed and, of its 53 medium findings, 30 fixed, 14 partly fixed, 6 kept as documented limits and
1 fixed before its last snapshot; 2 have no verdict (no fix touched them). It found no regression, and 25 new findings,
none of them high or medium. Not re-verified: the documentation changes of 2026-11-04, where the November round did not
change them again, and a smaller round of 2026-11-09 that followed the re-verification, whose changes this file
describes as they are in the tree: GPU ML-DSA signing also zeroizes μ and its copy of the context string, a GPU
context's `sync` queues a command of its own so that it also reports another context's sticky fault, the constant-time
tests compile their copies of ML-KEM and SLH-DSA with the libraries' options (ML-KEM's in the build's configuration),
and `mlkem_config_odr` checks that ML-KEM code that an application compiles with the other setting of the stack burn
cannot take the place of the library's. Not verified by the review: the FIPS 140-3 mode, built on the branch `fips140-3`
after that re-verification. A peer review of that branch as it was on 2026-11-12 read its code and ran it in a CI-like
container; its findings led to round 3 (2026-11-12 to 16). The same review checked the result on 2026-11-16 and 17, and
its findings led to round 4 (2026-11-17), which it re-read and ran on 2026-11-18, before the merge into `main`, leaving
low findings open; the developers' integration ran the round-4 tree on 2026-11-18
([docs/FIPS-140-3.md](docs/FIPS-140-3.md#tested-so-far)). Where a row below says what that mode does, it describes the
code, not a verified result. [Known issues](#known-issues) lists what remains open.

Decided by the maintainers on 2026-11-05 and done since, in the fix round of November 2026 that the review re-verified
on 2026-11-08:

- the randomness hook `opqc_set_randombytes` and the build option `OPENPQC_EXTERNAL_RANDOMBYTES` in place of the
  unprefixed `randombytes()`, with the OS RNG staying the default (the RBG row of Known issues; the
  [security notes](docs/SECURITY-NOTES.md#randomness-the-approved-rbg-is-the-integrators));
- ML-KEM's stack burn as the CMake option `OPENPQC_MLKEM_STACK_BURN`, ON by default. It makes each call need 48, 58 or
  68 KiB of stack and costs 1.3 % to 4.0 % of its cycles (the ML-KEM README's figure, which the review did not
  re-time). OFF keeps the named wipes, which `mlkem_stack_noburn` checks alone, and leaves the compiler's copies on
  the stack; the ML-KEM tests then check the library so built;
- in GPU ML-DSA, the range check of s1 and s2 in the signer (an operation with a malformed key gets an all-zero
  signature and `OPENPQC_ERR_INVALID_SECRET_KEY`, which a backend call without a status buffer returns before
  `OPENPQC_ERR_SIGNING_LIMIT`), and the zeroization of what verification computed (all but Â, after every call: about
  30 µs per launch at small batches and, at 8192 operations, 5 % to 10.5 % of a launch's device time and 4 % to 12.6 %
  of a call's time end to end, indicative figures from two runs on the laptop's RTX 3050 under DPC++, the project's
  and the review's; the ML-DSA README gives them per run) and, in FIPS 140-3 mode, of the whole workspace after
  create's self-test. The GPU
  API's ML-DSA calls run on the same backend functions, so all of this holds for them too.

Also done since then: the module boundary. In the library's own translation units the scheme layers and Core's C++
headers carry names of the library's (an inline namespace, `Core/abi.hpp`), so that templates an application compiles
with other configuration macros or flags cannot replace the library's (test `abi_symbols`), and the libraries are
compiled with hidden visibility, so that a shared build exports the C APIs only. The names carry the version: one
program may contain OpenPQC libraries of different versions, but of one version only one configuration (key generation
with and without the pair-wise consistency test, and ML-KEM with and without the stack burn, excepted). These
guarantees hold for the C APIs and the library's own code; an application that compiles the header-only C++ layers
itself gets copies in its own build configuration, with its own macros and flags. Install rules, a CMake package and
pkg-config files followed (test `install_consumer`), and a C program links the library without the C++ runtime (test
`c_link`). Then the unified GPU API (`openpqc/sycl.h`, `sycl.hpp`): one context type for all 18 parameter sets, a
status buffer on every call, the length of the message buffer, against which the device checks the offsets of the
signature calls (review finding F073; test `gpu_api`), and a shared GPU library that exports this API only, with its
testing interfaces in `OpenPQC::sycl_testing` and the backends' own C APIs internal (test `sycl_exports`). The review
has not re-verified these changes.
