# FIPS 140-3 mode: plan

OpenPQC is not a FIPS 140-3 module and has not been submitted for validation. This page is the plan for an opt-in
FIPS 140-3 mode, developed on the branch `feature/fips140-3`. It says what a module needs, what OpenPQC already has,
and the order in which the missing parts should be built. Where FIPS 140-3 is required today, use a validated module.

## The switch

`-DOPENPQC_FIPS140_3=ON` is the CMake option that the mode's features will hang on. It has no effect yet: a build with
it ON is the ordinary library and configuring prints a warning that says so. Each step below adds its part behind the
option; the default stays OFF, and the ordinary library keeps its current behaviour.

When the first step adds a compile definition, that definition must be part of the library's ABI tag (the inline
namespace planned for the module boundary), so that objects compiled with and without the mode cannot be linked into
one program without an error.

## What a module needs

FIPS 140-3 adopts ISO/IEC 19790:2012 (requirements) and ISO/IEC 24759:2017 (test requirements), with the changes of
NIST SP 800-140A to F, and the CMVP's Implementation Guidance (IG) interprets them. For a software module at security
level 1 that means, in short:

- a defined cryptographic boundary, and approved services that use approved algorithms only;
- an indicator that tells the caller whether a service it called was an approved one (IG 2.4.C);
- self-tests: a software integrity test before the module is used, a known-answer test (CAST) of each approved
  algorithm before its first use, and a pair-wise consistency test of every key pair the module generates;
- an error state: after a failed self-test the module gives no cryptographic output until it is reloaded;
- approved random bit generation: an SP 800-90A DRBG fed by an entropy source validated against SP 800-90B;
- zeroization of every sensitive security parameter, and the destruction of the intermediate values that FIPS 203
  §3.3, FIPS 204 §3.6.3 and FIPS 205 §3.1 ask for;
- algorithm certificates from the CAVP (tested through NIST's ACVP server) for every approved algorithm in the module;
- a security policy (SP 800-140B), and testing by an accredited laboratory before the CMVP issues a certificate.

## What OpenPQC has today

- The three standards' algorithms, checked against NIST's ACVP vectors and the reference implementations.
- Pair-wise consistency tests after KeyGen on the CPU: `OPENPQC_MLKEM_KEYGEN_PCT` and `OPENPQC_MLDSA_KEYGEN_PCT`, and
  `OPENPQC_SLHDSA_KEYGEN_PCT` as a compile definition.
- Known-answer tests when a GPU context is created, for ML-KEM and ML-DSA (not yet for SLH-DSA).
- Zeroization of the secrets and intermediate values on the CPU, with tests that search the stack for leftovers; the
  GPU backends wipe their workspaces, except for the gaps listed in SECURITY.md.
- Randomness from the operating system (`getrandom`, `arc4random_buf`, `BCryptGenRandom`), which is not an approved
  RBG.

## Steps, in order

1. **Boundary.** After the module-boundary work of the ordinary library (an ABI tag around the scheme layer and hidden
   visibility), FIPS mode builds a shared library as the module, exporting the approved services only. Decide with
   the laboratory whether the GPU backends are inside the boundary; until then the mode covers the CPU library.
2. **Services.** List the approved services (ML-KEM-512/768/1024, ML-DSA-44/65/87 with HashML-DSA, the twelve SLH-DSA
   sets with HashSLH-DSA, and the hash functions if offered). The standards' internal functions (`_internal`) and the
   derandomized calls (`_derand`) are testing interfaces: FIPS mode leaves them out of the module or marks them as
   non-approved. Add the approved-service indicator.
3. **Random bit generation.** An SP 800-90A DRBG (Hash_DRBG, HMAC_DRBG or CTR_DRBG) inside the module, seeded and
   reseeded as SP 800-90C describes. The ordinary library first gets a prefixed, registrable randomness hook with
   the OS RNG as the default; FIPS mode plugs the DRBG into that hook. The entropy source needs its own validation
   (an ESV certificate) or must come from a validated platform source.
4. **Self-tests and the error state.**
   - An integrity test when the library is loaded: an HMAC-SHA-256 (or a signature) over the module, with the
     expected value fixed at build time.
   - CASTs before first use: SHA-2, SHA-3 and SHAKE, the DRBG, HMAC, and ML-KEM, ML-DSA and SLH-DSA.
   - Pair-wise consistency tests always on in FIPS mode: the CPU options become mandatory, the GPU ML-DSA backend
     gets its definition from the option, and the batched GPU KeyGen of ML-KEM and of SLH-DSA get a test of their
     own (SLH-DSA's GPU context also gets a known-answer test at creation).
   - One error state for the whole module: after any failed test, every service returns an error until reload.
5. **Zeroization.** Close the remaining gaps that SECURITY.md lists for the GPU backends, add an explicit zeroization
   service (destroying a context already wipes it), and document what the module cannot reach (copies kept by the
   GPU driver, swap and core dumps of the process).
6. **Testing.** ACVP vectors for SHA-2, SHA-3 and SHAKE as ordinary tests; ACVP sessions against NIST's demo server
   for every approved algorithm; tests that force each self-test to fail and check the error state; a CI job that
   builds and tests FIPS mode.
7. **Documentation and validation.** The security policy (SP 800-140B format), the finite-state model, the tested
   operational environments, and the user guidance; then a laboratory engagement, the CAVP certificates and the
   CMVP submission, which take months and have a cost.

## Order with the rest of the work

Steps 1 and 3 depend on work in the ordinary library: the module boundary (ABI tag and hidden visibility) and the
prefixed randomness hook come first, in the planned fix round and the refactoring. Steps 2, 4 and 5 can start on this
branch once step 1's shape is known.
