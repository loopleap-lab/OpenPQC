# FIPS 140-3 mode: plan and status

OpenPQC has an opt-in FIPS 140-3 mode: designed for FIPS 140-3; not validated. No laboratory has tested it, no CAVP
certificate covers its algorithms, and it has not been submitted to the CMVP. This page is the plan of record for the
mode: what a module needs, which steps are done on the branch `fips140-3` (November 2026, built on the refactoring's
Phase 5), and what remains. The module itself is described in the draft of its security policy,
[FIPS-140-3-security-policy.md](FIPS-140-3-security-policy.md), whose
[open items](FIPS-140-3-security-policy.md#open-items-before-a-submission) are the main items that remain before a
submission; the "Open" lists of the steps below also hold the smaller ones that the developers know of. Neither list
claims to be complete. Where FIPS 140-3 is required today, use a validated module.

## The switch

`-DOPENPQC_FIPS140_3=ON` builds the shared library `libopenpqc` as the module (x86-64 Linux with GCC or Clang only).
Every object of the libraries, the GPU library included, is compiled with `OPENPQC_FIPS140_3=1` (and so is every test
but the 32-bit `hash_m32`), which is part of the library's ABI tag (`library_fips_v0_3_0` instead of `library_v0_3_0`,
`src/Core/abi.hpp`), so that objects compiled with and without the mode cannot be mixed in one program. In this mode:
- `BUILD_SHARED_LIBS` defaults to ON, and an explicit OFF is refused;
- the pair-wise consistency test after key generation is compiled into every scheme, on the CPU and on the GPU: the
  top-level `CMakeLists.txt` gives the library's objects the definitions `OPENPQC_MLKEM_KEYGEN_PCT`,
  `OPENPQC_MLDSA_KEYGEN_PCT` and `OPENPQC_SLHDSA_KEYGEN_PCT` in this mode only, and no option turns them off;
- configuring also refuses `OPENPQC_MLKEM_STACK_BURN=OFF`, `OPENPQC_EXTERNAL_RANDOMBYTES`, a static GPU library
  (`OPENPQC_SYCL_SHARED=OFF`), any platform other than x86-64 Linux with GCC or Clang as both the C and the C++
  compiler, and, with the tests, a linker without `--wrap`, which the test `core_rng` needs;
- configuring needs `nm`, with which the build checks the module after each link (step 1).

In every build, with or without the mode, configuring stops with a message if `OPENPQC_MLKEM_KEYGEN_PCT`,
`OPENPQC_MLDSA_KEYGEN_PCT` or `OPENPQC_SLHDSA_KEYGEN_PCT` is set in any form (the command line, a preset, a cache, a
parent project's variable). The first two were CMake options of earlier versions of the tree: a build directory
configured with them needs `cmake -U` for them, or a new directory. The test `fips_configure` checks each refusal with
its message: these options, another processor, system and pointer size, another compiler (a C compiler that CMake
identifies as TinyCC and a C++ compiler identified as SunPro, each a GCC or Clang made to look like one: the build's own
compilers if CMake identifies them as GCC or Clang, else a `gcc` or a `clang` from `PATH`, since CMake identifies some
compilers, the DPC++ nightly's Clang among them, as themselves whatever the flags say), a linker without `--wrap`, and
the three removed variables; it also checks that the configurations beside them are accepted. A case that cannot check
what it is for prints "NOT CHECKED" and fails the test in a build with `OPENPQC_REQUIRE_FULL_TESTS`.

Configuring accepts, as test configurations and not as the module as tested: build types other than Release (the
default), sanitizer builds (`OPENPQC_SANITIZE`), other linkers than GNU ld, and a library with a scheme left out
(`OPENPQC_WITH_MLKEM`, `_MLDSA` or `_SLHDSA` OFF, which the tests, the benchmarks and the examples do not allow). Which
of them have run is under [Tested so far](#tested-so-far). Without `OPENPQC_BUILD_TESTS` the four static library targets
of the source tree (`openpqc::core`, `openpqc::mlkem`, `openpqc::mldsa`, `openpqc::slhdsa`) hold no code: a program that
links one of them stops compiling with a message (`cmake/openpqc_fips_test_only.c`), and the benchmarks are not built.
With the tests they hold the module's code without its self-tests, for the tests only. The module is linked
`-Bsymbolic`, with immediate binding (`-z now`), without `RUNPATH` and with a version script that the build generates
(step 1); it is checked and sealed right after the link. Start from a new build directory: a cache of an ordinary
configuration keeps `BUILD_SHARED_LIBS` OFF.

The default stays OFF. The ordinary library changes in these ways:
- it gains two exported functions, `openpqc_fips_status()` (which returns `OPENPQC_ERR_NOT_APPROVED`, -13) and
  `openpqc_fips_service_approved()` (always 0), declared in the new installed header `openpqc/fips.h`, and the two
  status codes `OPENPQC_ERR_ERROR_STATE` (-12) and `OPENPQC_ERR_NOT_APPROVED` (-13), which `openpqc_status_string`
  names. Its installation holds the same headers as before plus `openpqc/fips.h` (Core's new internal headers
  `opqc_hmac.h`, `opqc_drbg.h` and `opqc_fips.h` are not installed in either build).
- **The pair-wise consistency tests after key generation are part of FIPS mode only** (the maintainers' decision of
  2026-11-17). The CMake options `OPENPQC_MLKEM_KEYGEN_PCT` and `OPENPQC_MLDSA_KEYGEN_PCT`, which gave the ordinary
  library these tests, no longer exist, and neither do the presets `pct`, `gcc-release-pct` and `clang-release-pct`.
  No ordinary library, CPU or GPU, has them. The tests that compile their own copy of the scheme code with the test
  (`mlkem_pct`, `mldsa_pct`, `slhdsa_pct`, their `_pct_fail`, `_pct_odr` and stack variants, and ML-KEM's other `_pct`
  tests: 24 in all) still run in every build. The tests of the library as built (`mlkem_pct_library`,
  `mldsa_pct_library`, and the pair-wise check of `mldsa_thread_stack`) run in FIPS builds only.
- **The GPU library's known-answer self-tests at the creation of a context are part of FIPS mode only** (the same
  decision). Before, ML-KEM's and ML-DSA's contexts ran one in every build, and SLH-DSA's in FIPS mode only. Now none
  runs outside the mode, so, by the maintainers' decision, **an ordinary GPU build has no known-answer check of the
  device**: only the project's tests compare the device's results with the CPU library's, which shares the math core.
  The ordinary GPU library holds neither the self-tests' code nor their answers (test `gpu_self_test`). Outside the mode
  only the developer definitions `OPENPQC_MLKEM_SYCL_CREATE_SELF_TEST`, `OPENPQC_MLDSA_SYCL_CREATE_SELF_TEST` and
  `OPENPQC_SLHDSA_SYCL_CREATE_SELF_TEST` compile them in: compile definitions for the project's tests, not CMake
  options, which no target of the libraries gives. The white-box tests compile the backends with them, and a build that
  gives them to every object (`CMAKE_CXX_FLAGS`) has the self-tests in its GPU libraries too. A test that needs the
  self-test reports by name, in an ordinary build, that it does not apply.
- in the GPU library of every build, ML-DSA signing now also zeroizes the challenges c and the result flags of its
  attempts after each call, and the C++ GPU layer (`openpqc/sycl.hpp`) reports every operation of a call refused with
  `OPENPQC_ERR_ERROR_STATE` as not computed, a code that only FIPS mode returns.
- the test `fips_configure` is registered in every build with the tests on x86-64 Linux with GCC or Clang (about half a
  minute; it configures the project in scratch directories). With the DPC++ nightly under CMake 4.5 or later, which
  names that compiler `DPClang`, the library's CPU objects are compiled without exceptions and RTTI as with the other
  compilers, so that a library built with it needs no C++ runtime.

Apart from these, the code of the ordinary build's functions is meant to be unchanged. Round 4 left it so: in the
developers' integration of the round-4 tree (2026-11-18) the ordinary `libopenpqc.a` is byte-identical to the round-3
tree's, built by GCC and by Clang, and the ordinary suites (GCC, Clang, GCC with the sanitizers, ML-KEM without the
stack burn) registered the same tests as on the round-3 tree, with the same results. Against the tree before the mode's
code, the evidence is that of the earlier rounds: no test that passed there fails in the ordinary build.

## What a module needs

FIPS 140-3 adopts ISO/IEC 19790:2012 (requirements) and ISO/IEC 24759:2017 (test requirements), with the changes of
NIST SP 800-140A to F, and the CMVP's Implementation Guidance (IG) interprets them. For a software module at security
level 1 that means, in short:

- a defined cryptographic boundary, and approved services that use approved algorithms only;
- an indicator that tells the caller whether a service it called was an approved one (IG 2.4.C);
- self-tests: a software integrity test before the module is used, a known-answer test (CAST) of each approved
  algorithm before its first use, and a pair-wise consistency test of every key pair the module generates;
- an error state: after a failed self-test the module gives no cryptographic output until it is reloaded;
- approved random bit generation: an SP 800-90A DRBG fed by an entropy source validated against SP 800-90B;
- zeroization of every sensitive security parameter, and the destruction of the intermediate values that FIPS 203
  §3.3, FIPS 204 §3.6.3 and FIPS 205 §3.1 ask for;
- algorithm certificates from the CAVP (tested through NIST's ACVP server) for every approved algorithm in the module;
- a security policy (SP 800-140B), and testing by an accredited laboratory before the CMVP issues a certificate.

## Steps and their status

1. **Boundary.** Done on the branch, with open items. The module is the shared library `libopenpqc` (in this tree
   `libopenpqc.so.0.3.0`, after the source tree's version number, which is not a release), every byte of it that the
   loader maps: the whole pages of its `PT_LOAD` segments. It is built with hidden visibility and linked with a version
   script that the build generates from the `OPENPQC_API` declarations of the module's headers (`openpqc/openpqc.h`
   with the schemes' C APIs, `Core/opqc_platform.h` and `Core/openpqc_core.h`), less the per-set functions of a scheme
   left out. It exports exactly those functions and no variable, whatever the compiler, its optimization level or its
   sanitizers; every other symbol, the C++ standard library's template instantiations included, is local. With all
   three schemes that is 195 functions: the C API of the 18 parameter sets, the runtime-selected API,
   `opqc_randombytes`, `opqc_zeroize`, `opqc_set_randombytes`, the version and algorithm table, `openpqc_fips_status`,
   `openpqc_fips_service_approved` and `opqc_fips_mark_non_approved` (test `fips_exports`). After each link of the
   module and before its seal, the build checks its dynamic symbol table (`cmake/openpqc_fips_check.cmake`): it must
   export exactly that list, import none of `memcpy`, `memmove`, `memset`, their `_FORTIFY_SOURCE` variants,
   `dl_iterate_phdr`, `dladdr`, `dladdr1`, `dlinfo`, `dlsym`, `sysconf` or `getauxval`, and import nothing outside its
   list of imports (a sanitizer's runtime aside). A failure stops the build and removes the library; the check runs in
   builds without the tests too. The module is linked `-Bsymbolic`, so that its own calls of its exported functions
   cannot be interposed (`fips_interpose`), with immediate binding (`-z now`), and without `RUNPATH`. It defines
   `memcpy`, `memmove` and `memset` (and their `_FORTIFY_SOURCE` variants) itself, hidden (`src/Core/opqc_fips_mem.c`),
   and finds its own image through the linker's `__ehdr_start` and `_DYNAMIC`, so it imports 12 functions from the GNU
   C library and its dynamic loader (`getrandom`, `getpid`, `clock_gettime`, the lock, once-guard and signal-mask
   functions, `__register_atfork`, `__errno_location`, `__stack_chk_fail` and `__tls_get_addr`; 11 when the Clang of
   the DPC++ nightly builds it, which enables no stack protector and so imports no `__stack_chk_fail`), plus the C
   runtime's four weak references, which the loader binds by name like any program's imports; `fips_integrity` (case
   `imports`) also fails on any other. Where libstdc++'s assertions are on (code that is not optimized, or
   `-D_GLIBCXX_ASSERTIONS`), a failed bounds check of `std::span` or `std::array` inside the module ends the process at
   once with a trap, through the module's own hidden `std::__glibcxx_assert_fail`: the module imports nothing from
   libstdc++. The module relies on its imports as part of its operational environment, and a process in which any of
   them is replaced or interposed, or in which anything outside the module changes its code or data, by whatever
   mechanism, is outside the tested configuration, where its guarantees do not hold (the security policy, Section 6.2,
   with the list and the known ways as examples). A position-dependent application works with the module
   (`fips_application_nopie`: no copy relocation of module data, since the module exports none). Outside the boundary:
   the GPU library, whose services are not approved until a laboratory decides otherwise (configuring refuses a static
   GPU library, which would hold the backends' functions in an installed archive); the header-only C++ APIs and scheme
   templates, compiled into the application; the testing interfaces (`OpenPQC::testing`, `OpenPQC::sycl_testing`),
   never installed; and the static libraries of the source tree (above). Open:
   - in a configuration with the tests, the static libraries hold the module's code and report the state operational
     and approved services without any self-test (they exist for the tests only);
   - a module with a scheme left out (possible only without the tests, the benchmarks and the examples) has fewer
     exports (87 without SLH-DSA, 153 without ML-DSA, 174 without ML-KEM) and runs only the CASTs of the schemes it
     holds; one of each was built from the round-4 tree (2026-11-18), passed the build check, was sealed, and loaded
     with the state operational, and a probe of round 4's review ran ML-KEM-768 and ML-DSA-44 services through the one
     without SLH-DSA (the indicator 1), but the tests need all three schemes, so no test has run on such a module;
   - the export list is made by running the C compiler alone on the headers: a compiler given together with a launcher
     (`CC="ccache gcc"`) stops the configuration, and a new header that `openpqc/openpqc.h` comes to include does not
     re-run it by itself (both fail closed: a configure error, or the build check refusing the module);
   - nothing the module outputs tells it apart from the ordinary library (`openpqc_version()` returns "0.3.0", the
     source tree's version number, in both): a module identifier is deferred to the first release, v1, which the
     maintainers decide; no version is decided.
2. **Services.** Done for the CPU library. Every one of the 171 per-set functions and the 13 runtime-selected ones
   checks the module's state when it begins and again when its computation ends, and sets the calling thread's
   indicator last: 1 only for an approved service that returned `OPENPQC_OK`. A call during whose computation the
   module enters its error state zeroizes its outputs and returns `OPENPQC_ERR_ERROR_STATE` with the indicator 0, and
   a call whose own draw from the DRBG fails returns -12 too; a key generation whose own pair-wise consistency test
   fails returns `OPENPQC_ERR_PCT` (and the module enters its error state). A result returned with `OPENPQC_OK` was
   complete while the module was operational at the second check. Tests `fips_services_inflight_drbg`, `_own_drbg` and
   `_pct` hold each call after its first check while the module enters its error state (or have its own draw fail),
   and each returns -12 with its outputs zero and the indicator 0; `_control` holds them with no failure; `_stress`
   shows, on free-running threads, that no wrong result is released (the security policy, Section 4.8).
   `keygen_from_seed` of ML-KEM and ML-DSA is approved, as the import of a key pair in its seed format, with its
   pair-wise consistency test: NIST's PQC FAQ (the answer last revised 2026-06-16) allows "generating the seed in one
   cryptographic module and then importing or exporting it into another cryptographic module", and says that
   ML-KEM.KeyGen_Internal(d, z) and ML-DSA.KeyGen_internal(ξ) "can be accessed for this purpose"; the seed must come
   from an approved RBG, which the module cannot check. Not approved (computed, indicator 0): ML-DSA's `check_sk` and
   `check_keypair` (FIPS 204 defines no key check), and HashML-DSA or HashSLH-DSA with a pre-hash weaker than the
   parameter set (the table in the security policy, Section 2.7). Tests `fips_services_*` and `fips_rng`. The testing
   interfaces (`OpenPQC::testing`, outside the module) are not approved services: each testing function clears the
   calling thread's indicator when it returns, and in the module's error state returns `OPENPQC_ERR_ERROR_STATE`
   in place of its result, its refusals included, without computing (test `fips_services_testing_interfaces`, the
   runtime-selected testing functions' own refusals included). Open: the laboratory's view of the seed import and of
   external μ; the testing functions check the state themselves only when they begin (a call that was computing when
   the error state began returns its result, with the indicator 0, unless a service of the module that it called checks
   again).
3. **Random bit generation.** Done in code; the entropy source is open. An HMAC_DRBG (SP 800-90A Rev. 1, SHA-512,
   256-bit security strength) inside the module is the source of every random value: instantiated with a 32-byte
   entropy input and a 16-byte nonce from `getrandom` (256 and 128 bits if the source's output has full entropy),
   reseeded with 32 bytes every 2^16 requests and after `fork()` (or any change of the process id), its health test at
   load (two NIST CAVP cases, with and without additional input); any entropy or DRBG failure enters the error state,
   and a draw that finds the module in its error state after generating outputs nothing. `opqc_set_randombytes`
   refuses every source with `OPENPQC_ERR_NOT_APPROVED`. Tests `core_drbg`, `core_drbg_cavp` (all 720 SHA-512 cases of
   NIST's CAVP files), `core_rng`, `fips_rng`, `fips_rng_entropy`, `fips_break_entropy`, `fips_break_drbg_generate`,
   `fips_state_draw_during_failure`. `core_rng` gives the DRBG a fixed `getrandom` stream, process id and clocks and
   compares, against answers computed outside the library, its first draws, the draw after the reseed interval, the
   draws after `fork()` in both processes, and the draw after a change of the process id without `fork()`, where no
   fork handler runs (it must reseed first, with 32 bytes); it also requires every `getrandom` request to pass the
   flags 0, in the ordinary build too. A DRBG seeded with zeros fails it, and so does a `getrandom` call with
   `GRND_NONBLOCK`. The module has no SP 800-90B entropy source: the operating system's must be a validated one, with an
   ESV certificate, in each operational environment. IG 9.3.A requires that certificate for a source inside the tested
   environment and allows no caveat in its place, so without one the module cannot be validated there (the security
   policy, Section 2.8, which also names what the laboratory must confirm about `getrandom`). Open: the module takes its
   entropy input from the C library's `getrandom` (and the process id and clocks of its personalization string from
   `getpid` and `clock_gettime`), imports to which the rule of step 1 applies; `-Bsymbolic` and `-z now` do not change
   which definition the loader binds. In a process that replaces them (the developers' probes, on the module of
   2026-11-12: the program's own definitions, `LD_PRELOAD`, and auditing libraries named in `LD_AUDIT`, in the
   program's `DT_AUDIT` or `DT_DEPAUDIT` entry or given to the loader's `--audit` option) a `getrandom` that returns
   zeros leaves the module operational, every process draws the same bytes, and the indicator reads 1; replacing
   `getpid` and `__register_atfork` together stops the reseed after `fork()`, and another `__tls_get_addr` made the
   indicator read 1 after a non-approved service. The same probes' other results (a changed copy passing the integrity
   test under another `memcpy`, `opqc_zeroize` leaving a buffer under another `memset`) no longer apply: the module
   defines those functions itself, `fips_integrity_preload` shows the first one failing, and the build refuses a module
   that imports them. A `getrandom` system call made by the module itself would take the C library's `getrandom` (and
   glibc's vDSO generator) out of the entropy input's path; the rule would still apply to the other imports.
4. **Self-tests and the error state.** Done, with open items. When the module is loaded: CASTs of SHA-256 and
   HMAC-SHA-256, the integrity test (a known-answer test of its own HMAC-SHA-256 on the compiled code that then computes
   the value, RFC 4231 cases 2 and 7; then HMAC-SHA-256 over the whole pages of every loaded segment but the end of the
   writable one's last page, in a canonical form for the bytes the loader writes, against the value stored after the
   link; a module without immediate binding, with `DT_FLAGS` or `DT_FLAGS_1` twice, or whose program header table or
   dynamic section breaks the layout that the test requires, is refused), then CASTs of SHA-512, SHA3-256, SHAKE128,
   SHAKE256, HMAC-SHA-512, HMAC_DRBG (two cases), ML-KEM-512, ML-DSA-44 (KeyGen, Sign and Verify; HashML-DSA-44 with
   SHA3-512, with SHA2-256 and with SHA2-384; and two rejection cases from NIST's ACVP ML-DSA specification, whose
   signing loops reject an attempt for each condition of FIPS 204, Algorithm 7, lines 23 and 28, as IG 10.3.A, Note 23,
   recommends), SLH-DSA-SHA2-128f (with HashSLH-DSA-SHA2-128f and SHA2-512) and SLH-DSA-SHAKE-128f. The three pre-hash
   cases are deterministic signatures from NIST's ACVP-Server files, compared on the SHA-256 of the signature. While
   they run, every signal that a thread can block is blocked on the thread that runs them and on any thread that
   waits for them (so no signal handler runs there; a signal sent to the process may go to another thread), and on the
   self-testing thread only the CASTs' own calls of services are served, after the integrity test has passed; any
   other call there returns -12 (tests `fips_state_signal`, `fips_state_timer`, `fips_state_reenter`,
   `fips_state_mask`, `fips_state_mask_error`). A fault that the self-tests' own code raises on that thread (`SIGSEGV`,
   `SIGBUS`, `SIGFPE`, `SIGILL`, for example from a stack too small for them) cannot wait: Linux ends the process with
   the signal's default action, and no handler of the application runs. The test copy of the module records each
   decision of the power-on self-tests in order, and every `fips_state_*` test checks IG 10.2.A's order against that
   record: the CAST of SHA-256 decides first, the integrity test third, after the CASTs of SHA-256 and HMAC-SHA-256
   have passed, and nothing is decided after a failure. Pair-wise consistency tests after every key generation, on the
   CPU always in this mode; a failure enters the error state. One error state for the whole module: every service
   returns `OPENPQC_ERR_ERROR_STATE` (-12) until the module is loaded again (in a new process, or by `dlclose` and
   `dlopen` in the same one when nothing else keeps it mapped), which runs every self-test again; that is also how the
   self-tests are repeated, an acceptable means at security level 1 (IG 10.3.E, Background). On the GPU (outside the
   boundary), in this mode only: a pair-wise consistency test of every key pair of the batched KeyGen of ML-KEM,
   ML-DSA and SLH-DSA, each of which fails closed when a part of the test does not run, and a known-answer test of
   every context at its creation (all three schemes). Neither is in an ordinary library (the maintainers' decision of
   2026-11-17, so an ordinary GPU build has no known-answer check of the device); outside the mode only the developer
   definitions `OPENPQC_*_SYCL_CREATE_SELF_TEST` of the project's tests compile the GPU self-tests in (above). A GPU
   self-test or pair-wise consistency failure fails the GPU call but does not enter the module's error state. A GPU call
   that runs an algorithm checks the module's state when it begins and again after waiting for its work (the security
   policy, Section 4.4). Tests `fips_break_*` (each CAST, and the integrity test's own known-answer test, made to fail
   in a test copy of the module; `fips_break_drbg_cast_null` makes the DRBG CAST's case without additional input fail),
   `fips_integrity` (a byte changed in `.text`, in the largest function of an SLH-DSA 256s parameter set, which only a
   service reaches after its state check, in `.rodata` (one a CAST reads, and one no self-test reads), in
   `.data.rel.ro`, `.dynamic`, GOT[0], GOT[1] or GOT[2], in the file's bytes in the last page of the executable segment,
   of the last read-only segment and in the first page of the writable one where the layout has such bytes, and the seal
   flag cleared; a library without immediate binding; `DT_FLAGS` and `DT_FLAGS_1` written a second time, both and each
   alone (`flags_twice`, `flags_twice_flags`, `flags_twice_flags_1`); `LD_PROFILE`; a changed `JUMP_SLOT` slot; a moved
   program header table (`phdr_outside`), and one written over the code in place of the header's page (`phdr_page`); the
   module's imports; every copy loaded lazily and immediately), `fips_integrity_aslr` (`DT_FINI` and `DT_FINI_ARRAY`
   changed by a predictable load base, with `setarch -R`), `fips_integrity_preload`, `fips_application_nopie`,
   `fips_preinit`, `fips_services_pct_*`; on the GPU `mlkem_sycl_faults(_pct)`, `mldsa_sycl_faults(_nopct)` and
   `slhdsa_sycl_faults(_nopct)` (in FIPS builds the backends compiled with `OPENPQC_FIPS140_3` alone, which must turn
   both tests on; one broken key pair beside passing pairs of the same launch), `gpu_layout` (the GPU library is
   compiled with the pair-wise consistency tests in this mode and without them in an ordinary build), `gpu_self_test`
   (the GPU libraries hold every answer of the three create self-tests in this mode and none in an ordinary build),
   `gpu_fips`, `gpu_fips_inflight` and `gpu_fips_testing_inflight`. Open:
   - with GNU ld a changed `JUMP_SLOT` value in the file is not detected: in the tested configuration the loader
     overwrites the slot before the module runs, so the change has no effect there; an environment that prepares lazy
     binding anyway is outside it, and ended in the error state in the environments tested. With lld's layout the
     slot's bytes are also mapped, as they are in the file, in another segment's page, so the integrity test itself
     refuses such a copy: lld builds show this case only as a refusal;
   - no regression test keeps the integrity test's known-answer test on the compiled code that computes the value
     (checked once in the GCC and Clang modules' machine code), or guards its test case 7;
   - several run-time requirements of the integrity test are defence in depth with no test that only they would fail,
     because a file sealed by the seal tool cannot break them without changing bytes that the value covers: a rule-2
     entry of the dynamic section twice, no `DT_NULL`, `PT_DYNAMIC`'s write flag against its segment's, an address
     entry at or above the load base, a `PT_PHDR` that names another table, a table past the file part of the header's
     segment;
   - IG 10.2.A's order inside the integrity test (its own known-answer test before its measurement) is pinned by no
     test, and the record of the decisions pins the order in which the verdicts are recorded, not when each test ran;
   - the forced failures of the three pre-hash CASTs (`mldsa_prehash_sha2_256_sign`, `mldsa_prehash_sha2_384_sign`,
     `slhdsa_sha2_prehash_sign`) and the dedicated order cases of `test_fips_state` (`order`, `order-error`) are
     registered (`fips_break_mldsa_prehash_sha2_256_sign`, `fips_break_mldsa_prehash_sha2_384_sign`,
     `fips_break_slhdsa_sha2_prehash_sign`, `fips_state_order`, `fips_state_order_error`) since the cleanup round that
     followed the integration of 2026-11-18, which did not run them;
   - the module holds several compiled copies of the header-only hash and HMAC code (the security policy, Section 2.6):
     whether each needs a CAST of its own is the laboratory's question. The pre-hash function is one linked copy shared
     by HashML-DSA and HashSLH-DSA (an inline function with external linkage of which the linker keeps one copy; with
     GNU ld the one compiled into the ML-DSA services), which the pre-hash CASTs cover; that rests on how the toolchain
     links, not on the source. The SLH-DSA services' own SHA-512 code (MGF1-SHA-512 and HMAC-SHA-512 of H_msg and
     PRF_msg, and H and T_l of the SHA2-192 and SHA2-256 sets) runs in no CAST, and neither does any pre-hash function
     other than SHA2-256, SHA2-384, SHA2-512 and SHA3-512 as such;
   - CAST coverage a laboratory may ask for: an "s" set of SLH-DSA, and SLH-DSA's own SHA-512 (above);
   - a call made from inside a CAST's own call, which only code run by a replaced import could make, is served (the
     rule of step 1);
   - with a C library whose `abort()` unblocks `SIGABRT` before it raises it (glibc 2.39 does; glibc 2.44, the tested
     one, does not), a stack-protector failure in the self-tests would run the application's `SIGABRT` handler on the
     self-testing thread before the process ends;
   - GPU evidence: `gpu_fips_error` needs AdaptiveCpp's JIT cache warm (`ctest` runs `gpu_fips` first; with a cold
     cache it fails, it does not pass); no test reaches the facade's path for an ML-DSA KeyGen whose device pair-wise
     test fails for some pairs (it returns `OPENPQC_ERR_PCT` with the passing pairs); the case `wait:kem_decaps` of
     `gpu_fips_inflight` shows the wait before the second check only while its 4096 decapsulations are still running at
     that check, which held with a wide margin on every device tried.
5. **Zeroization.** Done for what the module can reach. The DRBG's state is zeroized in the error state, after any
   refused DRBG call, at unload and at a normal process exit (not after `_exit()`, `abort()` or a fatal signal);
   `opqc_zeroize` is the zeroization service (it calls the module's own `memset`); a service during which the module
   enters its error state zeroizes its outputs, and so does a GPU call in FIPS mode; GPU ML-DSA signing now also wipes
   the challenges and flags of its attempts (every build). What the module cannot reach (registers at the end of the
   scheme operations, copies the operating system or the GPU driver makes) is listed in the security policy, Section
   9.3, and in [SECURITY.md](../SECURITY.md).
6. **Testing.** Partly done. ACVP vectors of SHA-2, SHA-3 and SHAKE run as ordinary tests (`core_hash_acvp`), the 40
   large-data tests too (`core_hash_acvp_ldt`, labels `slow` and `network`, 150 GiB); the 7,980 cases whose messages
   are not whole bytes are counted and not run, because they belong to registrations of every bit length and a
   byte-oriented module registers byte lengths. NIST's CAVP HMAC_DRBG vectors, RFC 4231 for HMAC, and the
   forced-failure tests of step 4. In a FIPS build NIST's ACVP vectors also run through the sealed module itself
   (`fips_vectors_mlkem`, `_mldsa`, `_slhdsa`, label `network`): a program linked with `libopenpqc.so` only, which
   first checks that it calls the sealed library of the build, runs all 435 ML-KEM cases, all 1,335 ML-DSA cases and
   912 of the 1,248 SLH-DSA cases through the per-set functions and, for the first case of each test group whose
   operation it offers, the runtime-selected API, with the indicator checked after every call, and positive controls
   that must fail (`fips_vectors_control_*`). Vectors alone cannot show that the hedged signing services use fresh
   randomness, so for the first case of every hedged test group the program also signs twice hedged and once
   deterministically through the module, verifies the three signatures, and requires the hedged ones to differ from
   each other and from the deterministic one; a hedged signing with the deterministic variant's randomness, or with a
   constant one, fails `fips_vectors_mldsa` or `fips_vectors_slhdsa`. What the program cannot compare, and why, is in
   the security policy, Section 2.7. The tests that check the ordinary build's randomness hook have FIPS-mode
   expectations: registration is refused and the DRBG stays the source (`core_rng_hook`, `core_rng_hook_external`,
   `mldsa_fresh`, `slhdsa_fresh`); `core_rng` checks the DRBG's requests to `getrandom` and its output (step 3); the
   constant-time check of ML-KEM's production Encaps (`mlkemNNN_ct_production`) runs on an m drawn from the DRBG in a
   child process whose entropy input it marks secret, so that valgrind checks the DRBG's reseed and generate too (on the
   module's objects as the tests' static libraries hold them, not the sealed shared object); the positive controls run
   on the test variants (`mldsa_fresh_control`, `slhdsa_fresh_control`, and `slhdsa_fresh_draws` for SLH-DSA's draws); a
   forced pair-wise consistency failure enters the error state, one key generation per process (`*_pct_fail`,
   `*_pct_odr`). Tests that cannot run their whole check say so: under `OPENPQC_REQUIRE_FULL_TESTS` a FIPS configuration
   needs Python, `strip`, `objcopy` and `eu-strip` (without them `fips_integrity` is reported as skipped and
   `fips_integrity_partial` runs the rest); the entropy-failure tests (`fips_rng_entropy`, `gpu_fips_error`,
   `gpu_fips_inflight`) fail where their seccomp filter cannot be installed; `fips_integrity_aslr` needs `setarch -R`
   and fails without it; the stack checks of HMAC and the DRBG (`core_hmac_stack`, `core_drbg_stack`) fail where they
   could run and do not (with GCC or Clang and no AddressSanitizer), and are reported as skipped in an
   AddressSanitizer build. Without that option these tests are reported as skipped. A FIPS build with AddressSanitizer
   and UndefinedBehaviorSanitizer loads, and passes the mode's tests where they have run: with GCC and with Clang at
   -O1, the FIPS set of 78 tests on the round-4 tree (the developers' integration of 2026-11-18), with GCC at -O1 also
   the batch tree's 92 in the peer review's container, and with GCC at -O0 the boundary and integrity tests (round 4's
   review). The integrity test reads the image in functions the sanitizers do not instrument, with the module's own
   `memcpy`, and the version script keeps the exports fixed; `fips_integrity_preload` is disabled there, since its
   preloaded library cannot come before the sanitizer's runtime. Before the changes of 2026-11-12 every process that
   loaded such a build ended in the integrity test, and before round 4 (2026-11-17) the Clang build exported one
   function of the C++ library too many, and a plain Debug build 27 objects and an import from libstdc++. Open:
   - the Wycheproof vectors (C2SP's Project Wycheproof) of ML-KEM and ML-DSA and NIST's known-answer files still run
     only on the test libraries, and SLH-DSA's 336 cases of the internal interface cannot run through the module,
     which does not offer it;
   - through the module, nothing shows that the other randomized services draw fresh randomness: the ML-KEM
     encapsulation cases do not compare their ciphertexts, and randomized key generation is not among the vectors;
   - tests that still pass having checked less: `fips_integrity`'s cases that depend on glibc (`profile`) or on the
     linker's layout (the page-end cases where the module has no such bytes, as with lld, the `flags_twice` copies where
     none can be made, and `jump_slot_unbound` with lld), which it reports by name as not applicable to the module (its
     cases that lack a tool or an argument print "NOT CHECKED" and fail under `OPENPQC_REQUIRE_FULL_TESTS`); without

     compilers cannot link such programs, the compiler cases without a compiler whose identity CMake lets them fake);
     `c_api_must_check`'s visibility probe; `check_must_check` without compilers; the indicator's starting value in
     `test_fips_load`;

     in such a container must run it without that filter or declare the requirement;
   - the constant-time copies of ML-DSA and SLH-DSA have no pair-wise consistency test in FIPS mode, so their `_ct`
     tests run a key generation without the test that the module runs (ML-KEM's copies follow the library);
   - until a FIPS CI job exists, no CI job builds a library with the pair-wise consistency tests: only the 24 tests that
     compile their own copies run in CI; and the branch's `.github/workflows/ci.yml` still names the removed `pct`

     calls; no ThreadSanitizer or MemorySanitizer run of the mode;
   - the cost of the module's own `memcpy`, `memmove` and `memset` (`src/Core/opqc_fips_mem.c`: the processor's string
     instructions above 32 bytes) against the C library's has not been measured; nor has the cost of the wait of every
     GPU call in FIPS mode (step 4);
   - no ACVP session against NIST's demonstration server;
   - a CI job that builds and tests the mode, to be set up after the branch is merged into `main`.
7. **Documentation and validation.** The security policy exists as a draft
   ([FIPS-140-3-security-policy.md](FIPS-140-3-security-policy.md)), with the finite state model, the services and the

## Verification and what the mode relies on

The review of October 2026 has not verified the FIPS 140-3 mode. A peer review of the branch as it was on 2026-11-12
read its code and ran it in a CI-like container: it found no case where the code does something other than what a
cited clause requires on a normal path, and its findings on evidence, on what the code trusts and on the documents led
to round 3 (2026-11-12 to 16). The same review checked the batch tree on 2026-11-16 and 17 (above): it found nothing
high, and its findings led to round 4 (2026-11-17), which it has not yet re-read. The mode relies on the refactoring of
November 2026, which the review has not verified either: the ABI tag (`src/Core/abi.hpp`), the C API's status codes
(`openpqc/common.h`, to which -12 and -13 were appended), hidden visibility of the library objects (only `OPENPQC_API`
functions are exported, which the version script now also enforces at link time), and the split of the testing
interfaces into `OpenPQC::testing` and `OpenPQC::sycl_testing`, which are not installed (tests `production_symbols`,
`sycl_exports`).
